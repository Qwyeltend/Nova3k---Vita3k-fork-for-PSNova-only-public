# Nova3K

Личный форк эмулятора [Vita3K](https://github.com/Vita3K/Vita3K), заточенный под одну игру — **Phantasy Star Nova** (PS Vita, PCSG00351 / PCSH00143).
Игра в репозиторий не входит: эмулятор запускает твой собственный дамп.

## Где взять APK

Сборка запускается вручную: вкладка **Actions** → *Nova3K Android* → **Run workflow**.
Готовый файл появляется в разделе **Releases → latest** как `Nova3K-<коммит>.apk`.
Первая сборка идёт около часа, следующие быстрее (кэш).

Приложение называется **Nova3K** и ставится рядом с обычным Vita3K, не заменяя его.
Все сборки подписаны одним ключом (`android/nova3k.jks`), поэтому новая версия ставится поверх старой без потери данных.

## Что изменено относительно Vita3K

| Изменение | Зачем |
|---|---|
| Имя пакета `org.nova3k.emulator`, название Nova3K | Не конфликтует с установленным Vita3K |
| Только arm64 | Быстрее сборка, x86-Android не нужен |
| ELF-дампы пишутся в `<папка эмулятора>/nova3k/elfdumps/<ID игры>/` | Папку можно открыть файловым менеджером; в Vita3K они лежали в недоступной `Android/data` |
| Своя сборка на GitHub Actions, запуск вручную | Только Android, без лишних платформ; изменения копятся без лишних сборок |
| Очередь показа кадров: кадр снимается с очереди до вызова функции игры (как до сборки 4080) | Исправляет зависание Nova на чёрном экране перед логотипом SEGA |
| Встроенный патч 60 FPS (включается галочкой **FPS Hack**) | Игра сама ставит себе 30 FPS; патч меняет 30 на 60, предварительно сверив байты |
| Логи шейдеров и дампы текстур в `<папка эмулятора>/nova3k/{shaderlog,textures}` | Доступны для анализа без root |
| Диагностика «текстура из поверхности» в логе (строки `Nova3K:`) | Ищем причину сломанных текстур редактируемого персонажа |
| `sceGxmTransferCopy`/`Downscale` из нарисованной GPU поверхности: эмулятор дожидается копирования, прежде чем рисовать дальше | Игра собирает текстуры кожи/волос/одежды рендером + копированием с `FRAGMENT_SYNC`; без ожидания модель получала недописанную текстуру (разный глитч каждый раз) |
| Копирование из GPU-поверхности при режиме памяти «double-buffer» (по умолчанию): данные сначала переносятся из теневого буфера в память игры | Иначе копировалась старая память, а затем у неё ещё и менялись местами красный/синий — отсюда старые, наполовину старые и «синие» лица/волосы |
| Кэш текстур ставит защиту памяти до чтения текстуры, а не после | Запись, попавшая между чтением и защитой, терялась — текстура оставалась частично старой (чёрные блоки на волосах) |
| Android: показ кадров в режиме FIFO и запрос у системы частоты экрана 60 Гц | Режим Mailbox на экранах 90/120 Гц держал кадры на экране разное время — 60 FPS, но рывками |
| Галочка **V-Sync** теперь видна и для Vulkan: вкл = FIFO, выкл = Mailbox | Сравнить плавность и задержку управления в одной сборке |
| Монитор производительности: раз в секунду строки `Nova3K perf` и `Nova3K threads` в логе; потоки получают понятные имена | Понять, что тормозит: процессор, графика, звук или ожидания |
| Монитор: строка `Nova3K waits` — какие вызовы эмулятора блокировали потоки игры дольше 1 мс; учёт заиканий звука и для SDL | Найти, на чём игра зависает на 70–200 мс несколько раз в секунду |
| Профилировщик: ~1000 раз/с смотрит, где находятся главный поток игры и поток `render` (строки `Nova3K profile`); счётчик ловушек памяти; сборка сохраняет `libVita3K.so` с символами | Понять, что выполняется во время зависаний: переведённый код игры, JIT-компилятор, обработка памяти |
| Монитор: имя ожидаемого семафора/флага в `Nova3K waits`; строка `Nova3K slow frame` для кадров > 50 мс | Разбор каждого медленного кадра главного потока |
| **Dynarmic (патч `tools/nova3k/patches/dynarmic`)**: при создании JIT сбрасывается кэш инструкций только для служебного кода, а не для всех 128 МБ буфера | Каждый новый поток игры стоил десятки миллисекунд — главный источник зависаний |
| ~~Закрепление потоков за большими ядрами~~ — проверено и откачено | Стало хуже: потоки стояли в очереди за 5 большими ядрами 20–35% времени |
| **Dynarmic (патч 0002)** + профилировщик: для выборок в переведённом коде определяется адрес кода игры (строки `Nova3K guest`); статистика JIT раз в секунду (`Nova3K jit`: сколько блоков переведено и за сколько, сколько выброшено и переведено заново из-за ловушек памяти) | Понять, чем именно занят JIT в медленных кадрах: тяжёлой работой игры, ожиданием в цикле или постоянным перепереводом кода |
| **Dynarmic (патч 0003)**: монитор эксклюзивного доступа без глобальной блокировки | Блокировки движка Aska крутятся в цикле до 512 раз на `LDREX/STREX`; в Dynarmic каждая такая инструкция любого потока шла через одну общую спин-блокировку и перебор 150 слотов — потоки толкались на ней. Теперь каждый поток работает со своим слотом, а атомарность обеспечивает сравнение-с-обменом в памяти |
| Ежесекундный отчёт монитора пишется в отдельном потоке `nova3k-report`; профилировщик выключен (`profiler_enabled`) | Отчёт занимал ~60 мс в потоке показа кадров и сам вызывал один пропущенный кадр в секунду |
| Монитор: время главного потока на процессоре и в очереди за свободным ядром в каждом медленном кадре; ядро каждого потока; вызывающая функция для ожиданий в профиле | Проверить, помогло ли закрепление ядер |
| **Встроенные профили игр** (`vita3k/config/src/nova3k_profiles.cpp`): для Phantasy Star Nova (`PCSG00351`, `PCSH00143`) сразу включены нужные настройки — Vulkan, VSync, Disable surface sync выкл., асинхронная компиляция, double buffer, FPS Hack, звук SDL. Пока пользователь не сохранил свои настройки игры, используется профиль; «удалить настройки игры» возвращает профиль | Игра работает «из коробки», без ручной настройки |
| **Переключатели Nova3K** (Настройки → CPU → Nova3K tweaks, у каждой игры свои): атомарные операции без блокировки (патч 0003), быстрый старт JIT (патч 0001), монитор производительности. Режимы: Авто (по профилю игры, у остальных игр выключено) / Вкл / Выкл. «Выкл» — ровно исходный код Vita3K (патч dynarmic 0004). В начале лога: `Nova3K: profile …, lock-free monitor …` | Наши изменения ядра не влияют на другие игры; если что-то сломалось, можно выключить одно изменение и проверить, виновато ли оно |
| **PSO2 (ветка `pso2`)**: профиль для `PCSG00141` и переключатель «PSO2 patches» (Авто = вкл. только для PSO2). Код — `vita3k/nova3k/pso2.cpp`. Патч «Начать игру»: в 6.31 пункт 0 титульного меню открывал только сообщение о закрытии сервиса; теперь он идёт тем же путём, что и остальные пункты, — в последовательность входа. Перед патчем проверяются байты исполняемого файла 6.31; другая версия не трогается. Журнал сети: строки `Nova3K PSO2 net:` (какие имена серверов игра ищет и куда подключается) | Вернуть путь к входу на сервер и увидеть, к какому серверу игра обращается, — без распаковки `pso2.cpk` |
| **PSO2 оффлайн: встроенный PhantasyServer** (автор Anton Maltsev, MIT — спасибо, без его работы это было бы невозможно). Копия сервера в `external/phantasyserver`, CI собирает её под Android (Rust, cargo-ndk) и встраивает в Nova3K; сервер стартует вместе с PSO2 и слушает только `127.0.0.1`. Перенаправление `*.pso2gs.net`, наш RSA-ключ в игре, асинхронный DNS и проверка PSN — части Nova3K | Играть в PSO2 Vita на Retroid без интернета и без чужих серверов |
| **PSO2: защита рендера в редакторе персонажа** (только PSO2). **Главное:** команды рендера PSO2 не берутся из кольцевого буфера контекста GXM. Vita3K считает свободные ячейки кольца счётчиком, а берёт их по кругу; когда команда освобождается не по порядку (`sceGxmFinish` посреди сцены), кольцо наезжает на ячейку, которая ещё ждёт выполнения, цепочка команд уходит в чужой кадр, команды выполняются и освобождаются дважды — вылет в редакторе персонажа 6.31 (в 1.000 кадр слишком мал, чтобы кольцо обернулось). Теперь каждая команда выделяется и освобождается отдельно. Также: Отложенные списки команд GXM копируются в сцену, а не прицепляются (защита на будущее: PSO2 их, как оказалось, не использует). Команды рендера, выделенные в обычной памяти, учитываются: повторное освобождение не роняет эмулятор, а пишется в журнал. Барьер Vulkan без изображения или без буфера команд пропускается (иначе драйвер Adreno падает на адресе 0x8). Журнал: `Nova3K PSO2 gxm:` / `Nova3K PSO2 vulkan:`. В `nova3k_crash.txt` — отчёты всех упавших потоков и команда рендера; после вылета при следующем запуске сохраняется `nova3k_logcat.txt` (системный журнал Android с сообщением аллокатора). ПСНова это не затрагивает | Пройти в редактор персонажа |
| **PSO2: диагностика рендера**. Строка `Nova3K PSO2 gfx:` раз в секунду: отрисовки (обычные и precomputed), отрисовки, пропущенные рендером, запросы видимости, поверхности, в которые писал процессор, уменьшения на видеокарте («downscales on the GPU»). Каждые ~5 секунд (первые ~2,5 минуты) — подробное описание одного кадра (`Nova3K PSO2 frame #N`): цели рендера каждой сцены, буфер глубины, число отрисовок, привязанные текстуры, все копирования/заливки (transfer). Трассировка итогового прохода, строки глубины и запросов видимости и снимки буферов убраны (задачу выполнили, а работу замедляли). Модели персонажей на системном драйвере Adreno не рисуются — используйте Turnip (Mr. Purple T30) | Поиск ошибок рендера в PSO2 |
| **PSO2: белый экран (плитка экспозиции)** (только PSO2). Каждый кадр PSO2 6.31 считает яркость сцены в буфере 512×256 из четырёх плиток 256×128 и при выводе на экран берёт правую нижнюю плитку. Vita3K считал размер такой «вырезанной» текстуры как полную строку буфера × высоту, плитка выходила за конец буфера на 1 КБ, и вместо отрисованной картинки читалась старая память — множитель яркости становился мусором. Теперь последняя строка считается по ширине самой текстуры | Убрать белый экран сцены |
| **PSO2: перезагрузка буфера после копирования процессором** (только PSO2, при разрешении ×1). Копирование, уменьшение и заливка (`sceGxmTransfer*`) в Vita3K выполняются процессором в памяти, но картинка-цель на видеокарте после этого не обновлялась. PSO2 6.31 каждый кадр уменьшает сцену 1408×768 в буфер 704×384; вода фонтана берёт из него картинку для преломления и без перезагрузки превращалась в сплошные белые столбы. Теперь после такой операции буфер помечается и перед следующим рисованием загружается из памяти. Белый экран это не исправляет. В строке `Nova3K PSO2 gfx:` — счётчик «surfaces reloaded after CPU transfers» | Правильная вода фонтана |
| **PSO2: белый экран (маска)** (только PSO2). Причина белого 3D-слоя: Vulkan-рендер Vita3K не эмулирует «маску» видеочипа Виты и вместо записи в маску рисует её значение цветом. PSO2 6.31 каждый кадр сразу после сборки 3D-картинки записывает маску со значением 1 — получалась белая заливка поверх 3D, под интерфейсом (областями, по форме зон экрана). Теперь программа обновления маски не пишет в цвет. Найдено по трассировке итогового прохода (`Nova3K PSO2 final …`): отрисовка `prim 0 idx 3 | uniforms fb0[1]: 1` после сборки сцены | Убрать белый экран |
| **PSO2: квесты «Exploration» для всех 15 локаций** (встроенный сервер). Кэмпшип → поле 1 → поле 2 (две раскладки локации из файлов игры с местными врагами) → босс локации (в лесу — арена с Рокбиром). Врата в следующую зону и босс появляются рядом с игроком, когда он дошёл до конца раскладки или победил 15 врагов. После босса — телепайп и награда. Генератор: `tools/quest_gen_all.py` (исследовательский репозиторий) | Каждый квест — несколько зон, свои враги, босс в конце |
| **PSO2: поиск ID модели врага в памяти** (только PSO2, временная диагностика). Встроенный сервер просит эмулятор (файл `pso2_server/nova3k_memscan.req`: первое появление врага, босс, команда `!scan`) найти в памяти игры значения «model id» из пакета появления врага и имена нескольких врагов; байты вокруг находок идут в журнал (`Nova3K PSO2 memscan`). Не больше 6 поисков за запуск, каждый — пара секунд | Понять, почему все враги рисуются Даганами |
| **PSO2: уменьшение сцены на видеокарте (скорость)** (только PSO2). Каждый кадр PSO2 6.31 дважды уменьшает картинку (`sceGxmTransferDownscale`: 1408×768 → 704×384 → 352×192). Vita3K делает это процессором: ждёт, пока видеокарта допишет кадр, копирует его в память, уменьшает и загружает обратно — по журналу около 600 мс ожидания в секунду, игра держалась на 40–50 кадрах. Теперь уменьшение делает сама видеокарта (линейный фильтр ровно 2:1 = среднее 2×2, как на Вите), без ожидания; сцену игра уменьшает двумя половинами (левая и правая по 704 точки), обе обрабатываются; результат лежит там, где его ищут следующие отрисовки. Если что-то не подходит (другой формат, сдвиг, сцена ещё записывается), используется старый путь — в журнале один раз `could not be done on the GPU`. Встроенный «FPS Hack» на PSO2 не влияет: игра ждёт только одну кадровую развёртку (`sceDisplayWaitVblankStart`), ограничения в 30 кадров в коде вывода нет — нехватка кадров была от этих ожиданий | 60 FPS в PSO2 |

## Планы

1. Расшифрованный код игры (ELF-дамп) → анализ.
2. Исправление глитчей текстур (полосы на коже персонажа).
3. ~~Патч на 60 FPS~~ — сделан, ждёт проверки.
4. Онлайн-кооператив через эмуляцию ad-hoc.
5. Свой упрощённый интерфейс под одну игру.
